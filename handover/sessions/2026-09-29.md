## The error, verbatim (Shaka's console, ToolBox → Sync)

```
PUT ptgcapi.ptgctools.workers.dev/write?path=data%2Faffiliate-commissions.json  500
Commission write failed: HTTP 500 — {"error":"btoa() can only operate on characters in the Latin1 (ISO/IEC 8859-1) range."}
🔄 Retrying failed save… ⏳ Retry failed, will try again in 30s   (forever)
```

## Cause

`writeFileRaw` in the worker base64-encodes the file for GitHub's contents API with `btoa(content)`.
`btoa` takes a "binary string" — one character per byte, code points 0–255 — and throws on anything
above that. The file has carried four U+2014 since 2026-09-21 and the cron still wrote it fine on
Sep 22 and Sep 23 08:00 UTC; what changed on Sep 23 is the **v5 redeploy from the Cloudflare
editor**, which gives the worker a current compatibility date, and the current runtime enforces the
spec where the old one let the characters through. From that moment every write — the daily cron at
08:00 UTC (caught inside `runCommissionSync`, logged, returned as `{success:false}`, nobody looks)
and ToolBox's `/write` (500) — failed, and the affiliates page froze at the last successful cron.

This was the "still latent" item in the 2026-09-20 notes ("`btoa()` dies on a non-Latin1 character").
It did not need an emoji username; a punctuation mark in a note was enough.

Why ToolBox said "Sync Complete": `syncReferrersFromAPI` called `saveData()`, which only **queues**
the GitHub write five seconds out and resolves at once, then showed the success modal. The only
sign of the failed write was the small red "NOT SAVED — changes are only in this browser" badge in
the page header (added 2026-09-21), truncated before the reason.

## Fix

**Worker v6** — `handover/ptgcapi-worker-v6.js` (v5 + one helper, one call site):

```js
function toBase64Utf8(str) {            // base64 of the UTF-8 bytes — what GitHub decodes
  const bytes = new TextEncoder().encode(str);
  let bin = ''; const CHUNK = 0x8000;
  for (let i = 0; i < bytes.length; i += CHUNK)
    bin += String.fromCharCode.apply(null, bytes.subarray(i, i + CHUNK));
  return btoa(bin);
}
…
content: toBase64Utf8(content),         // was btoa(content)
```

Checked in Node 22: the module parses; on a 1.3 MB sample carrying em-dashes and an emoji the helper
returns byte-for-byte what `Buffer.from(s,'utf8').toString('base64')` returns, and `btoa` on the
same sample throws "Invalid character". The chunked `fromCharCode` is there because
`String.fromCharCode(...bytes)` on a 1 MB array overflows the argument list.

**ToolBox** (`index.html`, `syncReferrersFromAPI` STEP 4): `await saveData(…)` →
`await saveDataImmediate(…)`. That one writes now and **throws** when the ledger did not persist, so
the failure lands in the existing catch as "Sync Failed" with the worker's message, and "Sync
Complete!" means the data is on GitHub. Verified the whole Babel block still compiles with the
pinned `@babel/standalone` from this repo's harness.

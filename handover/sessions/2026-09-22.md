# 2026-09-22 — the affiliates page showed some viewers a dashboard of zeros

Reported by Shaka: after yesterday's affiliates work the page reads correctly for him, but a
couple of referrers still see 0.00. They hard-refreshed, cleared caches, and one opened a browser
on a laptop he had not used in months. Still zeros.

That last detail is the whole diagnosis: **nothing was ever cached**, so nothing about clearing a
cache could help.

## What was checked first (all healthy)

- **The deploy is live and current.** `ptgc-ufo.com/index.html`, 957 KB, `last-modified`
  2026-09-22 10:27 UTC, `Cache-Control: max-age=600`, and it carries every marker from yesterday:
  `AFFILIATE_SYNC_UTC_HOURS` (the freshness badge), `normSettings`, `meetsThreshold===false` (a54),
  `volumeByPeriod` (a52). `git rev-list --left-right --count origin/main...HEAD` = `0 0`.
- **The data is live and correct.** `/public/commissions`, 704 KB, 71 referrers, 9 months,
  September `lastSyncDate` 2026-09-22T08:01:25Z (today's 08:00 cron ran). DomDoos: 66 buys,
  172.01M PTGC, $8,244.38, commission 3.44M PTGC, `meetsThreshold:true`, threshold $250.
- **The rendered page is correct.** Loaded `#/affiliates` live, expanded the Referrers Registry,
  searched DomDoos, expanded all 66 of his transactions: 527 lines of text, **zero** occurrences of
  `0.00` anywhere. The only zero on the page is September's `COMMISSIONS PAID 0 PTGC`, which is true.
- Not a second copy of the page: `goptgc.com` is the onboarding site and has no affiliate
  dashboard (no `ptgcapi` reference in its bundle, routes are staking/dao/statistics/onboarding);
  `x1prism.com` has no affiliate code either — the 09-20 note used it only as a neutral origin.
  `www.ptgc-ufo.com` does not resolve. `#/affiliates` on `ptgc-ufo.com` is the only one.

## The finding: an empty ANSWER was rendered as an empty PROGRAM

The page's HTML comes from this domain. Every **number** on it comes from a second host,
`ptgcapi.ptgctools.workers.dev`. One request. So anything that can answer that one request —
an ad or content blocker, a filtering DNS, a VPN, a corporate or carrier proxy — decides what the
page shows, and it is entirely outside this repo, this domain and the viewer's browser cache.

Reproduced on the LIVE site by overriding `window.fetch` to answer that one URL with `200` and `{}`:

```
REFERRERS 0 · TOTAL BUYS 0 · PTGC REFERRED 0 · SEA CREATURES — · USD VALUE $0
COMMISSIONS 0 PTGC · COMMISSIONS PAID 0 PTGC
Rate 2%  |  Min Threshold $10  |  ⟳ Last update unknown
```

A complete, healthy-looking dashboard, no warning anywhere. `{}` parses, so `res.ok` passed,
`JSON.parse` passed, `setData({})` ran, every `data?.x` fell through to its default, and each tile
summed an empty array to 0. `Min Threshold $10` is `normSettings`' default standing in for the real
250, and `Last update unknown` is the new badge with nothing to read — **the two tells to look for
in a viewer's screenshot.**

A **hard** failure was already honest: `fetch` rejecting (blocked outright) and a `500` (the
2026-09-20 outage shape) both reached `⚠️ Error Loading Data`. Only the soft failure lied, and the
soft failure is the one a blocker or a proxy produces.

Two things make it stick for a given viewer where a hard refresh cannot help:

1. It is not in their browser. A blocker extension, a DNS filter or a proxy sits on the network
   path and answers the same way for every browser on that machine or network — including one
   installed today.
2. **The worker sends no cache headers at all.** `jsonResponse` (worker v4) sets only
   `Content-Type` and `Access-Control-Allow-Origin` — no `Cache-Control`, no `ETag`, no
   `Last-Modified`. Verified against the live endpoint. An intermediary is therefore free to hold
   one copy of that body indefinitely with nothing able to revalidate it.

## The fix (index.html only — the worker was not touched)

`AffiliatesPage`'s one `useEffect`:

- `fetch(...?t=${Date.now()}, {cache:'no-store'})` — a per-load cache-buster plus no-store, so
  nothing in between may answer from a copy it is holding.
- `!res.ok` now reports the status (`Could not reach the commission data (HTTP 503).`) instead of
  the string `Failed to fetch`, which was indistinguishable from the browser's own network-error text.
- The body is read as text and `JSON.parse`d in a `try`, so an HTML captive-portal page and an
  empty body land on the same message instead of a raw `Unexpected token` string.
- **The shape guard.** The answer must look like what `getPublicCommissions` builds — `referrers`
  and `monthlyLogs`, both objects. Anything else throws:

  > The commission data came back empty or unreadable. Something between you and the data service
  > is the usual cause - an ad or content blocker, a VPN, a filtering DNS, or a work network. Try
  > again with those turned off, or on a different connection.

  An empty **program** is legitimate and still renders its zero state (`{}` for both). An empty
  **answer** is a failure and now says so. Do not relax this to "it parsed, so use it" — that is
  exactly what printed the zeros.
- Error screen container got `p-6` / `max-w-md` so the longer message wraps instead of stretching
  edge to edge. `tw.out.css` rebuilt (gotcha 26).

## Harness

`AFFIL_BAD=1` serves `{}` on `/public/commissions`; `AFFIL_BAD=<body>` sends that body verbatim.
The **default** stub moved from `{"entries":[]}` to `{"referrers":{},"monthlyLogs":{},"receipts":[]}`
— the guard correctly rejects the former (it is not the worker's shape), and every run that is not
about the affiliates page needs the zero state, not an error screen.

## Still open

- **The worker sends no cache headers.** One line in `jsonResponse` —
  `'Cache-Control': 'no-store'` — closes the stale-copy hole at the source, for every consumer, not
  just this page. Needs a manual paste into the Cloudflare editor (dash.cloudflare.com → Compute
  (Workers) → `ptgcapi` → Edit code); source of record is `handover/ptgcapi-worker-v4.js`.
  Not done this session — the page fix was the scope Shaka picked.
- **The endpoint is on `*.workers.dev`**, a shared hostname this project does not control. Moving
  it to a Workers custom domain (`api.ptgc-ufo.com`) would put the data on the same domain as the
  page, so anything that reaches the page reaches its numbers. DNS work in Cloudflare; not started.
- Every other reader of a third-party endpoint on the sibling pages has the same soft-failure
  question — this pass only covered the affiliates page. Worth an audit item if it recurs.
- **What to ask a viewer who reports zeros:** a screenshot of the header. `Min Threshold $10` and
  `Last update unknown` together are this failure. After this deploy they will see the error
  screen instead, which is self-identifying.

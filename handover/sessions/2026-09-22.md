# 2026-09-22 — the affiliates page showed some viewers a dashboard of zeros

Reported by Shaka: after yesterday's affiliates work the page reads correctly for him, but a
couple of referrers still see 0.00. They hard-refreshed, cleared caches, and one opened a browser
on a laptop he had not used in months. Still zeros.

That last detail is the whole diagnosis: **nothing was ever cached**, so nothing about clearing a
cache could help.

## What was checked first (all healthy)

- **The deploy is live and current.** `ptgc-ufo.com/index.html`, 957 KB, `last-modified`
  2026-09-22 10:27 UTC, `Cache-Control: max-age=600`, and it carries every marker from yesterday:
  `AFFILIATE_SYNC_UTC_HOURS` (the freshness badge), `normSettings`, `meetsThreshold===false` (a54),
  `volumeByPeriod` (a52). `git rev-list --left-right --count origin/main...HEAD` = `0 0`.
- **The data is live and correct.** `/public/commissions`, 704 KB, 71 referrers, 9 months,
  September `lastSyncDate` 2026-09-22T08:01:25Z (today's 08:00 cron ran). DomDoos: 66 buys,
  172.01M PTGC, $8,244.38, commission 3.44M PTGC, `meetsThreshold:true`, threshold $250.
- **The rendered page is correct.** Loaded `#/affiliates` live, expanded the Referrers Registry,
  searched DomDoos, expanded all 66 of his transactions: 527 lines of text, **zero** occurrences of
  `0.00` anywhere. The only zero on the page is September's `COMMISSIONS PAID 0 PTGC`, which is true.
- Not a second copy of the page: `goptgc.com` is the onboarding site and has no affiliate
  dashboard (no `ptgcapi` reference in its bundle, routes are staking/dao/statistics/onboarding);
  `x1prism.com` has no affiliate code either — the 09-20 note used it only as a neutral origin.
  `www.ptgc-ufo.com` does not resolve. `#/affiliates` on `ptgc-ufo.com` is the only one.

## The finding: an empty ANSWER was rendered as an empty PROGRAM

The page's HTML comes from this domain. Every **number** on it comes from a second host,
`ptgcapi.ptgctools.workers.dev`. One request. So anything that can answer that one request —
an ad or content blocker, a filtering DNS, a VPN, a corporate or carrier proxy — decides what the
page shows, and it is entirely outside this repo, this domain and the viewer's browser cache.

Reproduced on the LIVE site by overriding `window.fetch` to answer that one URL with `200` and `{}`:

```
REFERRERS 0 · TOTAL BUYS 0 · PTGC REFERRED 0 · SEA CREATURES — · USD VALUE $0
COMMISSIONS 0 PTGC · COMMISSIONS PAID 0 PTGC
Rate 2%  |  Min Threshold $10  |  ⟳ Last update unknown
```

A complete, healthy-looking dashboard, no warning anywhere. `{}` parses, so `res.ok` passed,
`JSON.parse` passed, `setData({})` ran, every `data?.x` fell through to its default, and each tile
summed an empty array to 0. `Min Threshold $10` is `normSettings`' default standing in for the real
250, and `Last update unknown` is the new badge with nothing to read — **the two tells to look for
in a viewer's screenshot.**

A **hard** failure was already honest: `fetch` rejecting (blocked outright) and a `500` (the
2026-09-20 outage shape) both reached `⚠️ Error Loading Data`. Only the soft failure lied, and the
soft failure is the one a blocker or a proxy produces.

Two things make it stick for a given viewer where a hard refresh cannot help:

1. It is not in their browser. A blocker extension, a DNS filter or a proxy sits on the network
   path and answers the same way for every browser on that machine or network — including one
   installed today.
2. **The worker sends no cache headers at all.** `jsonResponse` (worker v4) sets only
   `Content-Type` and `Access-Control-Allow-Origin` — no `Cache-Control`, no `ETag`, no
   `Last-Modified`. Verified against the live endpoint. An intermediary is therefore free to hold
   one copy of that body indefinitely with nothing able to revalidate it.

## The fix (index.html only — the worker was not touched)

`AffiliatesPage`'s one `useEffect`:

- `fetch(...?t=${Date.now()}, {cache:'no-store'})` — a per-load cache-buster plus no-store, so
  nothing in between may answer from a copy it is holding.
- `!res.ok` now reports the status (`Could not reach the commission data (HTTP 503).`) instead of
  the string `Failed to fetch`, which was indistinguishable from the browser's own network-error text.
- The body is read as text and `JSON.parse`d in a `try`, so an HTML captive-portal page and an
  empty body land on the same message instead of a raw `Unexpected token` string.
- **The shape guard.** The answer must look like what `getPublicCommissions` builds — `referrers`
  and `monthlyLogs`, both objects. Anything else throws:

  > The commission data came back empty or unreadable. Something between you and the data service
  > is the usual cause - an ad or content blocker, a VPN, a filtering DNS, or a work network. Try
  > again with those turned off, or on a different connection.

  An empty **program** is legitimate and still renders its zero state (`{}` for both). An empty
  **answer** is a failure and now says so. Do not relax this to "it parsed, so use it" — that is
  exactly what printed the zeros.
- Error screen container got `p-6` / `max-w-md` so the longer message wraps instead of stretching
  edge to edge. `tw.out.css` rebuilt (gotcha 26).

## Harness

`AFFIL_BAD=1` serves `{}` on `/public/commissions`; `AFFIL_BAD=<body>` sends that body verbatim.
The **default** stub moved from `{"entries":[]}` to `{"referrers":{},"monthlyLogs":{},"receipts":[]}`
— the guard correctly rejects the former (it is not the worker's shape), and every run that is not
about the affiliates page needs the zero state, not an error screen.

## Where the triage stopped — PICK UP HERE

One affected referrer was asked to open `https://ptgcapi.ptgctools.workers.dev/public/commissions`
directly. He reported **"a ton of text"** — the raw JSON loaded for him — and then stopped replying.

**That does not clear the blocker hypothesis, and this is the trap to not fall into next time.**
Content blockers and privacy shields filter the requests a PAGE makes to another origin; a
top-level navigation typed into the address bar is usually left alone. Brave Shields and uBlock
both behave that way by default. So "the URL works when I open it" and "the page cannot fetch it"
are perfectly consistent, and the direct-URL test alone proves only that DNS and TLS to that host
work from his machine.

Two follow-ups were sent and never answered. They are the next step:

1. **Ctrl+F his own username in that text.** If it is there, the real data reaches his machine and
   his figures exist in it — which narrows it to the page-context block above.
2. **Reload `#/affiliates` on the new build** and say which of three things he sees. The decision
   tree, which is the whole value of yesterday's change:
   - **real numbers** -> resolved, whatever it was;
   - **the "Error Loading Data" screen** -> confirmed page-context block. That is a line in the
     onboarding ("allow ptgc-ufo.com in your blocker"), not a DNS migration;
   - **still 0.00** -> the interesting one. On this build, zeros from a missing payload are
     impossible, so zeros would mean they come from REAL data (a different bug entirely) or he is
     not looking at `ptgc-ufo.com`. Get a screenshot before touching anything.

Until one of those comes back, nothing here is worth building. The page no longer lies, which was
the actual defect; the rest is one viewer's network.

## The custom-domain option, costed — so it does not need re-deriving

DNS checked live 2026-09-22: `ptgc-ufo.com` NS are `ns29`/`ns30.domaincontrol.com` (**GoDaddy**),
A records `185.199.108-111.153` (GitHub Pages). `goptgc.com` (ns23/ns24) and `x1prism.com`
(ns37/ns38) are on GoDaddy too. **`ptgc-ufo.com` has no MX records** — no mail to break, which is
normally the scariest part of a nameserver move.

A Cloudflare Workers **custom domain requires the zone to be on Cloudflare DNS**, so
`api.ptgc-ufo.com` is not a small addition — it means moving the whole domain's nameservers from
GoDaddy to Cloudflare first. Cons, honestly:

- a mistake recreating the records takes down the **entire site**, not just the API — a much bigger
  blast radius than the problem being solved;
- 24-48 h propagation to watch through;
- DNS and the Worker then sit in one Cloudflare account: a single login becomes the failure point
  for both (weigh against the unfinished 2FA work in `security-buy-sell-2026-09-14.md`);
- it adds a DNS record, a certificate and a route binding that can each break silently in a way
  that looks **exactly** like the bug just fixed;
- and it is not a guaranteed cure — it removes the shared-blocklisted-hostname problem, which is
  the *likely* cause, not a confirmed one for any particular viewer.

Mitigation if it is ever done: the `workers.dev` URL stays enabled alongside a custom domain, so
ToolBox's authenticated `/sync` POSTs keep working through the transition.

**The cheaper route, with no DNS work at all:** every other number on the dashboard already comes
from `raw.githubusercontent.com`. If the worker's daily cron also wrote its public projection into
this repo as `data/affiliate-public.json`, the affiliates page would read it from the same place as
everything else — no new third-party dependency, and the page stops being the one surface with its
own private failure mode. Cost: a worker change (hand-paste in the Cloudflare editor) and respect
for the file-size trap that caused the 09-20 outage.

**Recommended ordering** (given to Shaka): the one-line `Cache-Control: no-store` in the worker
first, then the referrer's answer, then decide. Two or three people out of 71, now looking at an
honest error screen instead of a convincing lie, is not an emergency.

# Part two: the zeros were never the network — the Registry read a rotten summary

The morning's fix was real but it was not their bug. Shaka's reports, assembled: one referrer sees
zeros **on the main affiliates page, not on his own card**; a couple of people in a chat said "some
are showing zero"; and yesterday **DomDoos read 0.00 for Shaka too**, until he forced a manual
`/sync` from ToolBox and the dollar amounts appeared. That last fact is the tell — it was never a
viewer's network, it was the data, and forcing a sync papered over it for a day.

## What the page was doing

`referrerStats` builds every Referrers Registry row. It walks the monthly logs to compute
`commPaid`, `commPaidUsd` and `pending` correctly — and then took the other three columns straight
off the payload's per-referrer summary block:

```js
return{name:username,wallet:r.wallet,buys:r.totalBuys||0,ptgc:r.totalPtgc||0,usd:r.totalUsd||0,…}
```

Two sources in one row, and `||0` dressing a missing field as a clean zero.

## Measured against the live payload, 2026-09-22

Of 71 referrers (68 with real activity):

| | count |
|---|---|
| correct | 24 |
| wrong but non-zero | 41 |
| **reads 0 while having real buys** | **3** — `ziom` (1 buy, $135.28), `cocktail` (6, $858.18), `TPB` (1, $9.93) |
| legitimately no activity | 3 |

The rot is an **overwrite, not an accumulate**: DomDoos' `totalPtgc` is `426,641,915.64`, exactly
his **February** figure, and his `totalUsd` is `38,355.09`, exactly his **March** one. His real
lifetime is **266 buys / 1.414B PTGC / $124,142.24**. For `ziom`/`cocktail`/`TPB` the fields were
never written at all.

**Why Shaka never saw it.** The ALL-TIME tiles sum the monthly logs and only fall back to the
summary block when there are no logs at all — so the top of the page has always been right
(1,404 buys / 6.14B / $520,652, verified against the data). Had they used the summary they would
have read 608 / 2.53B / $240,578 — **53.8% low**. So the headline looked healthy while a referrer
looking for his own name found zeros. The 🏆 Leaderboard, reachable from the same page, built its
rows from the raw summary object too, so its ranking was wrong as well.

## The fix

One `lifetimeByUser` map, memoised on `data`, summing `buysCount` / `ptgcAmount` / `usdAmount` per
username across every monthly log, plus a `lifetimeOf(username)` reader. Everything now takes those
three numbers from it:

- **Registry rows** — was `r.total*`, now `lifetimeOf(username)`.
- **Leaderboard** — was `{username,...r}` sorted on the stale `totalPtgc`, now overridden from the map.
- **The referrer card** — was correct, but by keeping its **own** second copy of the sum inside
  `getReferrerDetails`; that copy is gone and it reads the map like everything else.
- **The `stats` fallback** that summed `r.total*` when the monthly logs came out empty is deleted.
  It answered "no data" with wrong data; no entries in any month means zero, and zero is honest.

**Nothing on this page reads `referrers[x].totalBuys/totalPtgc/totalUsd` any more.** Only `wallet`
and `addedDate` still come from that block — the two fields the worker writes once and correctly.

## Verification

The `AFFIL_DATA` fixture reproduces the live shape for free: its `referrers` entries carry only
`wallet` and `addedDate`, no `total*`, so before the fix every Buys / PTGC / USD cell in the
Registry was `r.totalBuys||0` on a field that does not exist — necessarily 0. After
(`probes/affil-registry.js`, new):

| row | Buys | PTGC Bought | Value (USD) |
|---|---|---|---|
| alice | 2 | 1.00M | $500.00 |
| carol | 1 | 400.00K | $200.00 |
| bob | 1 | 80.00K | $40.00 |

`rowsWithZeroBuysAndZeroUsd: 0`. Alice's **card** reads TOTAL BUYS 2 / PTGC BOUGHT 1.00M — matching
her row exactly, so removing its private sum changed nothing. ALL-TIME tiles unchanged at
3 / 4 / 1.48M / $740 / 40.00K. The morning's two paths still behave: the valid empty program
renders its zero state, `AFFIL_BAD=1` renders the error screen. `npm run compile` clean.

The `Comm. Paid 0 / $0.00` and `Pending 0` cells that remain are **correct** — a referrer never
paid, and a referrer fully paid up. Do not "fix" those.

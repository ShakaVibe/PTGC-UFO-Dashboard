## a60 — Ledger correctness pass (`ledger.html`)

Three defects, all fixed.

### 1. "Received PTGC" was counted as a buy

`ledger.html`'s second pass walks PTGC transfers **into** a DAO wallet whose hash is not already
in `seenHashes` — i.e. PTGC that arrived in a transaction the DAO wallet did **not** send. Every
one of those was typed `ptgc_buy`, so it landed in the "PTGC Buys" tile and its PTGC total, while
the dashboard's DAO Buys chart (wallet-sent, PLS-paid swaps only, `build-dao-buys.mjs`) counted
none of them. Two "buys" numbers on the same site, from the same files, disagreeing.

Measured over the full treasury files (`/tmp/orphan2.mjs`, this session):

```
treasury-recent (8 mo): inbound PTGC 84, already-seen (outgoing) 84, dao->dao 0, ORPHAN 0
full files (all time) : inbound PTGC 492, already-seen 412, dao->dao 0, ORPHAN 80
    2023-10   2 rows   265,145.82M PTGC   from 0x8d0c8e35f7      <- the treasury's own funding
    2025-05   2 rows        62.26M PTGC   from two addresses
    2025-07  76 rows         5.31M PTGC   from 0x0a0990fe8b x76
```

**None of the 80 came from a known router**, and none are inside the 7-month picker today — so
this changes nothing currently on screen and everything about the first month that a payout,
airdrop or refund lands in. Picking Oct 2023 would have read "2 PTGC Buys · 265.1B".

Fix: those rows are typed `transfer` with a 📥 icon (description unchanged, "Received N PTGC"),
so they count under Transfers and filter with them. A row is a buy only if the wallet paid for
it, which means it has an outgoing transaction. The `isFromRouter` escape hatch is gone with a
comment saying why: a router delivering PTGC to the DAO in someone else's transaction is a
donation, not a treasury buy.

### 2. Month buckets were cut at the viewer's local midnight

`new Date(year, month-1, 1)` / `new Date(year, month, 0, 23,59,59)` compared against block
`timeStamp`s, which are UTC seconds. Now `Date.UTC(...)`, and so are the picker, the default
month, the `treasury-recent.json` window gate (`oldestPicker`) and every time printed on a row.
The summary heading carries a small **(UTC)**.

Proved with `probes/ledger-digest.js` (new) — the same page, five runs, per-month tile counts
plus the set of transaction hashes in the table:

Before: a Sydney viewer and Shaka disagreed about 5 of the 7 months on offer. After: every
viewer's page is the same page.

### 3. A stalled treasury workflow was invisible

Only a 30 %-opacity "Last updated" line at the very bottom, with no year and no age. Now
`LEDGER_STALE_MS` 8 h / `LEDGER_DEAD_MS` 7 d at module scope (the same rule index.html applies to
`burn-summary.json`, because the same ~5-runs-a-day pipeline writes both — gotcha 21): past 8 h an
amber banner above the summary, past 7 days a red one and every tile reads "—". `formatLastUpdated`
prints UTC, adds the year once it is not this one, and the footer carries the age.

## a61 — Pipeline failure handling (`scripts/fetch-coingecko-data.js`, `scripts/lv-snapshot.js`)

a29 already fixed the two workflow-level halves of this item (one hourly workflow, named-file
`git add`, and a "Report step failures" step that turns any `continue-on-error` step into a red
run). What was left was the two scripts that write a partial figure as if it were a whole one.

**fetch-coingecko-data.js.** `fetchOHLCV` and `fetchTrades` returned `[]` on any error, so a
rate-limited pool was indistinguishable from a quiet one; the per-pool loop added the rest to the
token total and the save-time validation never looked at `result.errors`. A 7D volume missing its
biggest pool passes every reader gate (fresh < 24 h, positive, monotonic) and shows up as "7D
volume", "vs 7D avg" and PTGC Value Generated at a fraction of the real figure.

Now: both return `null` on failure, `fetchPoolsBatch` reports a failed chunk, and each token
carries `complete: {volume, transactions, liquidity}`. At save time a figure that did not come back
whole is published as the **previous** run's value with a `carriedFrom` stamp, and the append-only
history files get no point for that token at all (one understated point is permanent — they are
averaged per day). `main().catch(console.error)` — a stack trace and exit 0 — is now
`process.exit(1)`.

Tested by running `main()` against stubbed fetchers (`/tmp/cgtest/run.js`, five modes):

```
ok        -> vol7d 600 (both pools)  complete {v:1,t:1,l:1}   liq points 1  txn points 1
volfail   -> vol7d 1000 (previous)   complete {v:0,t:1,l:1}   carriedFrom {volume:...}   liq 1  txn 1
tradefail -> txns carried            complete {v:1,t:0,l:1}   liq 1  txn 0
liqfail   -> liquidity carried       complete {v:1,t:1,l:0}   liq 0  txn 1
throw     -> exit 1, nothing written
```
(without the fix, `volfail` would have published 300 — one of two pools — as a fresh 7D total.)

**lv-snapshot.js.** `fetch()` never checked `res.statusCode`, so a DexScreener error body parsed
fine and produced a zeroed row; nothing rejected a row with no pairs or no liquidity. Four
snapshots a day means one empty answer knocks ~25 % off that day's average liquidity in the L/V
Analyser and the Growth Projection percentiles, permanently. Now a non-2xx rejects (with the body
excerpt), and a token with `pairCount === 0` or `totalLiquidity === 0` refuses the write and exits
non-zero. Tested against a local HTTP server (200 resolves, 500 rejects) and with stubbed answers:
empty-pairs and zero-liquidity both leave the history file untouched.

Note on the 20 zero-UFO rows already in `lv-snapshots.json`: they are all 7–12 Jul 2026, when this
script still pointed at the pre-migration UFO contract whose pools were drained. They are history,
not failed fetches — **left alone**; pruning them is Shaka's call.

## a53 — Holder tier file age and null Squid (`index.html`)

`token-allocation.json` was trusted regardless of age and short-circuited both fallbacks, so a
stalled builder served week-old tiers to every visitor as current. The step is gated to rebuild
every 6 h and the pipeline lands ~5×/day with gaps up to 5 h, so a healthy file can be ~11 h old:
`ALLOC_STALE_MS` 14 h (an "as of" label), `ALLOC_DEAD_MS` 36 h (treat as missing and fall through).
The file's own `lastUpdated` is carried as `asOfTs`, not the moment it was read, so the 2 h
localStorage copy keeps telling the truth. The Holders share card reads the same file under the
same rule.

Second half: `fetchHolderTiers` computed `Math.max(0, totalHolderCount - counted - excluded)` with
`totalHolderCount` null (PulseScan's `/counters` is documented as intermittent) → `NaN`, and the
consumer's `result.squidAndBelow || 0` turned that into a flat "0" cached for two hours. Now null in,
null out, and the consumer uses `Number.isFinite`.

Harness. New env `PS_COUNTERS_DOWN=1` fails only `/counters` while the holder pages answer:

```
allocation file 3 h (real) -> tiers from the file, no label
allocation file 20 h       -> tiers from the file + "AS OF 20H AGO"
allocation file 40 h       -> file ignored, live scan runs

UFO, /counters 500s, allocation file 40 h:
  ORIGINAL -> 🔱 0  🐋 19  🦈 104  🐬 518  🦑→🐚 4.66K     <- the 40-hour-old file, unlabelled
  NEW      -> 🔱 0  🐋 0   🦈 0    🐬 0    🦑→🐚 —          <- unknown says unknown
```
(the zeros are the harness's empty holder-page stub; the point is the "—".)

### What the timestamp actually means — read this before changing the wording

Two things were found in the worker while scoping it, and both shaped the design:

1. **The sync writes to GitHub only when it found new transactions** — `if (newTxCount > 0)`
   in `runCommissionSync`. So `monthlyLogs[month].lastSyncDate` is when the data last
   **changed**, not when it was last **checked**. A quiet week leaves it a week old with
   nothing wrong.
2. **`getPublicCommissions` strips `lastAutoSync`.** The sync does write a top-level
   `lastAutoSync` on the same condition, but `publicData` is built from `referrers`,
   `monthlyLogs` and `receipts` only, so it never reaches the page. Confirmed against the live
   endpoint: the response has exactly those three keys.

Hence: the badge has **no amber state and never says "overdue"**. From the browser we cannot
tell a quiet stretch from a stalled worker, and a warning that cries wolf on a healthy system
is worse than none. The schedule is printed as the fact it is — `AFFILIATE_SYNC_UTC_HOURS=[8]`,
from the Cloudflare cron trigger `0 8 * * *`, read off the dashboard 2026-09-21 (Trigger events
→ Cron triggers: "Runs at 08:00 AM", "Next Tue, 22 Sep 2026 08:00:00") — never derived from the
timestamp. **If that cron is ever changed, change that constant.**

The five closed months in the live data all carry a `lastSyncDate` of 08:00:xx UTC on the 1st of
the following month, which is the same cron; September's 13:56:57Z on 2026-09-21 is a manual
`/sync` POST from ToolBox, not a scheduled run.

### Open: a true "last checked"

If the badge should ever say "Checked 12 min ago" and go amber on a missed run, the worker needs
a heartbeat that does **not** re-upload the whole commission file (that file is ~692 KB and
already broke the endpoint once by crossing 1 MB — gotcha in the table). Cheapest honest options:
Cloudflare KV written in `scheduled()` and returned by `getPublicCommissions`, or a tiny separate
GitHub file. Not built — it needs a worker deploy by hand in the Cloudflare editor. The one-line
version of this is simply adding `lastAutoSync: data.lastAutoSync || null` to `publicData`, which
gives the page a top-level "last changed" without the per-month scan, but still not "last checked".

instead of the empty `{"entries":[]}` default, so the affiliates page renders with data;

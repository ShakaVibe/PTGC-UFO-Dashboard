### A · RPC pool re-probes a dead primary in the critical path, stalling every in-flight call for a full timeout
- severity: P2
- effort: S
- area: perf
- lines: index.html:365, 379–399
- confidence: HIGH
- evidence:
  `if(_rpcIdx!==0&&Date.now()-_rpcSince>RPC_STICKY_MS){_rpcIdx=0;}` (381)
  `const j=await _rpcOnce(RPC_ENDPOINTS[idx],body,timeout);` inside `for(let i=0;i<n;i++)` (384–387)
- scenario: rpc.pulsechain.com hangs (the Aug-2026 pattern: 15 s hangs, not fast refusals). The pool
  fails over correctly, but every 120 s the first call after the sticky window resets `_rpcIdx=0`, and
  every concurrent call issued in that tick (a log scan has CONC=3 chunks plus the boundary search)
  also starts at index 0 because `_rpcIdx` only moves after one of them fails. Each of those calls
  waits its full timeout — 8 s for eth_call/eth_getBlockByNumber, 20 s for eth_getLogs — before
  rotating. A multi-minute delivered/fees scan therefore stalls 20 s every 2 minutes while the primary
  is down, with the "reading fees" spinner up. Not a correctness bug; the sticky/failover logic
  otherwise works (429 → throw → rotate; no endpoint is stuck forever).
- fix: Remember `_rpcFailedAt[idx]` and skip an endpoint that failed within the last N seconds, or
  probe the primary in the background (a cheap `eth_blockNumber` on a timer) instead of in the caller's
  path.

### A · getLogsRange halves the range on a total transport failure as if it were a range-cap error
- severity: P2
- effort: S
- area: perf
- lines: index.html:398–399, 589–600
- confidence: HIGH (mechanism traced; wall-clock cost depends on whether endpoints refuse or hang)
- evidence:
  `console.error('RPC error (all '+n+' endpoints failed):', …); return{result:null};` (398–399)
  `const msg=(r&&r.error&&r.error.message)||'no result field';` … `if(depth<10&&(b-a)>250){ … split … }` (589–598)
- scenario: all three endpoints are unreachable or hanging. `rpcFetch` resolves `{result:null}` after
  3 × 20 s; `getLogsRange` reads that as "no result field" and halves the chunk, sequentially, six
  times (10 000 → 156 blocks) before `noteLogError` — up to 7 × 60 s ≈ 7 min per scan before the first
  `null` propagates, and the fee effect (6937–6958) then retries the whole thing twice more. The
  visitor sees the loading state for ~20 min before RETRY appears, instead of "chain read failed"
  within a minute. A JSON-RPC-level rate-limit error (HTTP 200 + `{error:{code:-32005}}`, which some
  public nodes send instead of 429 — unverified for these three) takes the same halving path, which
  multiplies requests against a node that is already throttling.
- fix: Have `rpcFetch` return `{error:{transport:true,message}}` on pool exhaustion and make
  `getLogsRange` return `null` immediately for a transport error (only split on a real RPC error
  object); treat `-32005`/"rate limit"/"too many requests" error codes as rotate-worthy in `rpcFetch`.
